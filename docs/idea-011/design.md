---

## 一句话定位

把"判页/判数"从服务器搬到手机端本地跑，服务器只负责下发流程、收结果、处理异常。

## 为什么现在慢（已实测，非推断）
| 环节 | 耗时 | 数据来源 |
|---|---|---|
| 手机截图 → PNG 编码 → 上传 | 2~14 秒，中位 7 秒 | relay 日志 620 个样本（11-08~11-10） |
| 服务器 → 本地脚本下载 | **3~18 毫秒** | 本机回环实测 |
| 服务器端判页（tesseract） | 判得出来 1.3~1.8 秒；**判不出来 4~11 秒** | BENCH.md 实测 |
| 服务器端判数（四张卡战力） | 7.9 秒 | BENCH.md 实测 |

> 完整数据见 `BENCH.md`。一句话：**判页最贵的时候（判不出来）要 11 秒，而这正是脚本最容易卡住的时候。**

关键结论：
1. **瓶颈是"手机上传"那一段，不是服务器。** `/media/<token>` 是 `web.FileResponse` 读本地磁盘，回环 3MB 只要 3~18ms。
2. **也不是图片大小或手机编码。** 同一天内同样 3MB 的图，快的 2 秒、慢的 14 秒 —— 编码速度恒定，解释不了 4 倍差。
3. **根因是 tailscale 走了美国中继。** 11-08 有 87% 走直连（中位 2s），11-09 之后只剩 22%（中位 7s）。见下方「已排除项」。

## 判页/判数为什么能快（ALAS 的做法，已读码）

| | ALAS | 我们现状 |
|---|---|---|
| 输入 | 25×25 局部图（坐标写死） | 2460×1080 全图 |
| 模型 | densenet-lite-gru，**3.25MB**，字符集 39 | tesseract，几十 MB，几千字 |
| 目标 | 直接出数字 | 先出整段文字再正则 |
| 耗时 | 毫秒 | 1~2 秒 |

代码位置（ALAS）：
- `module/exercise/exercise.py:62` — `Digit(OCR_EXERCISE_REMAIN, letter=(173,247,74), threshold=128)`
- `module/exercise/assets.py:17` — `area=(1153,140,1178,165)`，25×25
- `module/ocr/models.py` — 模型注释写明 size 3.25MB / 39 类 / 准确率 99.43%

**启示**：模型体积不是障碍（3MB 级别），我们脚本里的 `REGION_*` 坐标也已经在做局部裁剪，缺的只是"别传全屏图"。

## 方案

```
服务器（我）                         手机 App
├─ 写流程、改判据、看报告            ├─ 本地循环：取帧 → 找图/判页 → 点击
├─ 下发：流程 JSON + 模板图（几十 KB）├─ 要读数字：裁 25×25 → 本地 OCR
└─ 收：结果、异常帧、局部小图（几 KB）└─ 关键节点回话：到位/打完/卡住
```

流程用 JSON 状态机描述，不下发可执行代码（安全边界清楚，改流程不用重打包）：

```json
{
  "start": "list",
  "states": {
    "list": {
      "detect": {"template": "jjc_list.png", "min": 0.85},
      "on_match": {"tap": [1234, 567], "next": "info"},
      "timeout": 10, "on_timeout": "fail"
    }
  }
}
```

## 已验证事实（2026-11-10）

1. **MIT 协议**，改了不用开源、不用回馈上游。
2. **上游 105 个提交里，`accessibility/` 目录零改动。** 他们改的是 `network/upstream`（6 文件）、`wake`（4 文件）、语音和 UI。
3. **relay 的 Android 端已经在用 MediaProjection + VirtualDisplay + ImageReader**（`ScreenCapture.kt` 726 行），而且处理过 Android 14 的"每次会话只能 createVirtualDisplay 一次"限制，VirtualDisplay 常驻缓存。
4. **点击注入已有**：`ActionExecutor.kt` 1841 行，`dispatchGesture` + 节点点击降级链。
5. **仓库是单仓两产物**：`plugin/`（Python 服务端，现在跑着的）+ `app/`（Android，包名 `com.axiomlabs.hermesrelay`）。
6. **插件目录是软链**：`~/.hermes/plugins/hermes-relay → ~/.hermes/hermes-relay/plugin`，服务 `WorkingDirectory` 就是仓库根 —— **合并即改线上，没有部署缓冲**。

## 已排除项（别再重复调研）

- **不是服务器性能问题**：3MB 本地转发，进程跑了 28 天没重启。
- **不是 tailscale 带宽死限**：最快能跑 1 秒/3MB（约 24Mbps）。
- **不是手机 PNG 编码慢**：同机同图耗时差 4 倍，编码速度恒定。
- **不是 AutoX.js 能替代的路子**：它的瓶颈同为 MediaProjection + Bitmap 转换，且是脚本运行时不是常驻服务。
- **不需要做 ADB 独立虚拟屏**：那套（`am start --display` + 系统级虚拟屏）能让游戏后台跑，但用户手机固定专门跑脚本，游戏前台即可，省 3~4 周。

## 关键约束

**服务器编不了 APK**（实测）：
```
java: 无   gradle: 无   Android SDK: 无
磁盘: 剩 5.7G (85%)   内存: 3.7G
```
Android 编译要 JDK17 + SDK(3~5G) + Gradle 缓存 + 编译时 2~4G 内存，这台机器装不下。

→ **App 改造必须在 Windows 上编，或走 GitHub Actions。** 用户电脑当前关机，待装打包环境。

## 风险

1. **fork 维护**：改动面约 40 行插入 + 1500 行新增。冲突只可能发生在两个插入点，新增文件永不冲突。维护 `PATCHES.md` 记录插入内容即可。
2. **上游大版本**：小版本（1.13.0→1.13.1）是补丁，风险低；大版本重构可能动 `accessibility/`。
3. **服务端合并无缓冲**：软链 + 源码直跑，合并即上线，需 restart + 验证 + 可 reset 回滚。
4. **反作弊**：读屏 + 手势注入在游戏侧可能被识别，概率未知，非保证。
5. **官方替代**：若 Hermes 官方出移动端自动化，本方案让位。评估见下。

## 关于「只升 App 不升服务端」

**结论：技术上可行，但与"改造"本身矛盾。**

- 协议向后兼容，旧服务端 + 新 App 能跑（现有 bridge 端点不变）。
- 但我们要加的 `/local/*` 端点在服务端侧，**不发指令就没法触发**。
- 除非走**端上自治**：App 内置定时任务 + 自己拉流程配置（HTTP 从服务器取），服务端完全不动。
- 端上自治的额外好处：上游服务端怎么改都不怕；坏处是调度、异常上报要另做。

→ 设计时优先把协议面压到最小（3 个端点甚至 0 个），是降耦合的关键。
