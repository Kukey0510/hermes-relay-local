# 块16 · 执行器：步骤 DSL + App 内解释器（最小子集）

> 2026-11-13 立。前置：块15（拉到的 `steps` 是结构化的）。契约见 `docs/idea-012/13-scripts-api契约.md`。
> **本块只做第一版：线性步骤 + 固定的几个 op。分支/循环/条件一律不做**，用户口径是「脚本写啥就是啥，尽量限制」。

## 目标

脚本不再靠服务器 Python 一步一步点，改成手机自己按步骤跑。
判页、读数、点按在本机完成（`/localvision`、`/read` 的逻辑已经在 App 内，直接调内部 API，不要再走 HTTP 回自己）。

## 支持的 op（就这五个，多一个都不加）

| op | 参数 | 语义 |
|---|---|---|
| `tap` | x, y | 点屏幕坐标 |
| `tapText` | text | 在无障碍树里找文字命中并点击，找不到算失败 |
| `wait` | ms | 等待，最大 10000 |
| `probe` | expect, timeout_ms | 抓帧判页，等于 expect 才过；超时算失败 |
| `read` | field | 读一个数值字段（走 `DigestReader`），结果写进运行日志 |

每个 step 通用可选字段：`id`（日志用）、`timeout_ms`、`retries`（默认 0）。

## 失败语义（用户 2026-11-13 定）

- 单步失败 → 按 `retries` 重试 → 仍失败 → **停手**，不再往下跑
- 停下后：写一条事件（`level=error`）交给块17 的上报通道；**第一版不自己想办法解决**
- 不许自己加「猜一个坐标继续点」这类兜底逻辑

## 安全闸（硬拦，写死在 Guard 里）

### 白名单怎么取、怎么校验（2026-11-13 技术核实后定）

- **每脚本一份 `targetPackages`**（契约字段），不搞全局白名单：脚本天生绑游戏，全局白名单挡不住「碧蓝的脚本点到交错界面」
- **校验必须用实时前台包名，不许用 `/bridge/status` 的 `current_app`**——实测那个字段滞后，
  游戏在前台时它报 `com.android.systemui`，拿它当判据等于没拦。
  取法：`AccessibilityService.rootInActiveWindow?.packageName`（现查），
  拿不到时退回 `HermesAccessibilityService` 里 `TYPE_WINDOW_STATE_CHANGED` 记录的事件包名
- **每个 step 执行前复核一次**（不缓存跨步），不符即停手
- **能拦住什么 / 拦不住什么，写进代码注释和报告**：
  - 拦住：脚本跑错 App、运行中主动切到别的 App、前台是桌面/系统界面
  - 拦不住：检查与点击之间毫秒级的用户手动切走（Android 没有「只允许向某包点击」的能力）。
    所以脚本里**优先用 `tapText`（无障碍节点点击）而不是坐标 `tap`**，把风险降到节点级别

### 其余三条硬禁

1. **禁系统级操作**：不实现也不透传任何音量键、电源键、系统设置跳转、`send_intent`、`broadcast`
   - **DSL 永不提供音量 / 亮度 op**：App 清单里有 `MODIFY_AUDIO_SETTINGS`，
     意味着技术上它能改音量；所以必须在 DSL 层就掐死，不留接口
   - 亮度：App 没有 `WRITE_SETTINGS`，改不了系统亮度，只能改自己窗口 —— 也别做
   - `press_key` 本来就只有 home/back/recents/notifications/quick_settings 这几个全局动作，**不许加进 DSL**
   - 真正的风险不是「调系统 API」，而是**坐标点到了系统 UI**：下拉通知栏里的亮度条 / 音量条都在
     `com.android.systemui` 上。所以 Guard 另加一条：前台包名是 `com.android.systemui`
     或以 `com.android.settings` 开头 → 立即停手（`guard_system_ui`）
2. **禁消费类兜底**：任何失败路径都不许自动点击兜底坐标
3. **禁并发**：同一时刻只允许一个脚本运行，第二个请求直接拒（`run_in_progress`）

> 白名单只约束**脚本**（2026-11-13 用户定）：用户自己在手机上手动点、手动改亮度音量不归它管，
> 也不该被脚本运行状态影响。


## 入口：两条（2026-11-13 用户定）

1. **主用法：服务器下发**。新增 bridge 路由 `POST /script/run`，body `{"scriptId": "..."}`。
   App 侧要在三处都登记（这是闭集注册表，漏一处真机就 403）：
   - `bridge/BridgeCapabilities.kt` 的 `routes` 表：`POST /script/run` → `permanent(SCREEN_CONTROL)`
   - `network/relay/BridgeCommandHandler.kt` 的 dispatch 分支
   - 只读路径集合**不要**加（它是写操作）
2. **留口子：手机上也能点**。脚本详情页一个「运行」按钮，直接调同一个 runner，不走 HTTP


## 交付形态

新增包 `app/src/main/kotlin/com/hermesandroid/relay/script/runtime/`（**这里全部是新文件**），
加上 `BridgeCapabilities.kt` / `BridgeCommandHandler.kt` 各加一处接线（见上面「入口」一节，只许加这几行）。

- `ScriptStep.kt` — `@Serializable` 的步骤模型 + 从 JSON 反序列化 + 未知 op 直接 `UnsupportedOperationException`
- `ScriptRunner.kt` — `suspend fun run(script, access: ScriptAccess): ScriptRunResult`
  - `ScriptAccess` 是由调用方注入的接口（点击 / 读屏树 / 抓帧判页 / 读数 四件事），
    **runner 自己不许直接碰 AccessibilityService、ScreenCapture、DigestReader** —— 方便单测
- `ScriptGuard.kt` — 白名单与禁用动作判定，纯函数，可单测
- `ScriptRunResult` / `ScriptRunLog` 数据结构（日志落盘留给块17，这里只产出内存对象）

UI 侧只加最小入口：脚本详情页一个「运行」按钮，跑起来后把最近 5 条步骤结果直接显示在详情页。
**不做**进度条、不做停止按钮（下一块补）。

## 单测（必须有，全是纯逻辑）

- 正常四步全过 → result 成功、步骤计数正确
- `probe` 超时不匹配 → 停手，后续步骤不执行
- `retries=2` 且前两次失败第三次成功 → 继续
- 包名不在白名单 → 直接拒绝，一步都不执行
- 未知 op → 抛异常而不是静默跳过
- `wait` 超过 10000 被夹到上限
