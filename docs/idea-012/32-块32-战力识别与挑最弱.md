# 块32 · 演习「挑最弱对手」：端上战力识别 + tapWeakest

> 2026-11-14 立。前置：块20 判据、块18 读数。执行方：Codex Cloud。
> 目标：让手机自己认出四张对手卡的战力和，点最小那张。**这是正式版竞技场脚本的最后一块硬缺口。**

## 背景（已核实，不用重查）

- 演习列表页四张卡，每卡两行黄字战力（主力 / 先锋），2460×1080 下位置固定：
  - 卡位 `CARD_SLOTS`：`(430,150,320,410)`、`(800,150,320,410)`、`(1170,150,320,410)`、`(1540,150,320,410)`
  - 战力带相对卡位 `POWER_REL = (13,225,305,99)`，带内是两行（主力在上、先锋在下）
- 服务器侧现有做法（`bl_lib.scan_cards`，OCR + tesseract）：今天 3 帧实测**只读出 2/4 张卡**。
  收窄到「只框黄字、二值化、单行模式、数字白名单」后提升到 **4/4 张卡**，说明问题在框法和预处理，不在识别本身。
- 服务器侧「模板匹配」可行性已量过（`~/.hermes/data/localvision/blhx/build_power_digits.py`）：
  - 单模板 + 灰度相关：**68.7%**（150 个样本）—— 不可用
  - 多模板 + 宽高比惩罚（留一法）：**96.7%**，且数字 `7` 一个样本都没有
  - 结论：模板匹配精度不够、样本还得靠运气攒，**不选它做主线**
- 参考开源实现（本地 `~/.hermes/data/azurlane/repos/alas`、`pilot`）都用自训 OCR 模型读同一区域，
  说明「框法固定 + 颜色过滤 + OCR」是主流正解；他们手机版是塞 PRoot 容器，我们不学。

## 方案（用户已拍板：准确性和速度优先，包体不管）

**用 ML Kit Text Recognition v2（bundled 版，不依赖 Google Play 服务），走「裁图 → 预处理 → 识别 → 求和 → 点最小」。**

预处理按服务器实测有效的路子来：
1. 按 `CARD_SLOTS[i] + POWER_REL` 裁战力带
2. HSV 取黄字（H 18~42、S≥90、V≥140），把非黄像素刷成白底、黄字刷成黑字（二值化）
3. 放大 4 倍（INTER_CUBIC），减少小字丢笔画
4. 把 8 个小图**拼成一张**横排大图，一次调 ML Kit（省 8 次推理开销）
5. 解析每段数字 → 每卡 `主力 + 先锋` 求和 → 取最小 → 点该卡中心

**新 op：`tapWeakest`**

```json
{"op":"tapWeakest","fallback_index":0,"min_confidence":0.5,"dry":false}
```

- 内部：截图一次 → 上述流程 → 点战力和最小的卡中心
- `dry:true` 时只返回读数不点（给调试和单测用）
- 识别失败的卡跳过；**四张全失败**时按 `fallback_index` 点该卡，并在事件里写 `power_fallback`
- 返回/日志必须带：每卡两个读数、和、选中索引、耗时 ms、每段识别置信度（ML Kit 没给置信度就写 `-1`）

## 硬约束

1. **不新增服务器依赖**，全部在 App 内完成（用户明确：不改服务端）
2. 不碰 `assets/pages.json`、`assets/reads.json`、`assets/templates/`（块18/块20 正在动这些文件）
3. 不碰 `bridge/`、`data/*Policy*`、`ui/screens/BridgeScreen.kt`（块31 正在动）
4. ML Kit 依赖必须是 **bundled**（`com.google.mlkit:text-recognition:16.x`），不要 `play-services-mlkit-*`
5. 二值化 + 拼图逻辑必须抽成**纯函数**（输入 Bitmap/像素数组，输出数字列表），可 JVM 单测，
   不要和 ML Kit 调用糊在一个方法里
6. 老脚本不受影响：`tapWeakest` 是新增 op，未知 op 时的行为不变
